# 0001. Фиксировать архитектурные решения в ADR

- Статус: Accepted
- Дата: 2026-11-15

## Контекст

Проект совмещает исследование протокола и MVP. Решения о владении BLE-сессией, навигации, настройках и границах модулей уже принимались, но их причины фиксировались только в `AGENTS.md`, который описывает текущее состояние. При изменении требований становится непонятно, какие ограничения обязательны, а какие были следствием обстоятельств: есть риск повторно обсуждать закрытые вопросы или случайно отменить важное ограничение.

## Решение

Каждое значимое архитектурное решение оформляется отдельным ADR в `docs/adr/`. ADR хранится в репозитории рядом с кодом, имеет сквозной номер, статус и дату. Принятый ADR не редактируется: новое решение оформляется новым ADR, старый получает статус `Superseded by NNNN`.

## Последствия

- Причины решений сохраняются и доступны без истории чатов и обсуждений.
- Перед изменением архитектуры агент обязан проверить существующие ADR.
- Появляется дополнительный документ на каждое значимое решение; для локальных правок ADR не требуется.
- `AGENTS.md` остаётся описанием текущего устройства, ADR — историей и обоснованием.

## Альтернативы

- **Только `AGENTS.md`.** Описывает «как есть», но не сохраняет причины и не показывает, какие решения уже отменены.
- **Обсуждения в чатах и issue.** Плохо находятся, теряются при смене инструментов и не версионируются вместе с кодом.
- **Комментарии в коде.** Объясняют локальные детали, но не решения уровня модулей и приложения.
