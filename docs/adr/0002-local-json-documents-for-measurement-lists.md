# 0002. Хранить списки измерений в локальных JSON-документах

- Статус: Accepted
- Дата: 2026-11-15

## Контекст

Пользователь должен сохранять много именованных списков измерений, открывать их снова и продолжать работу. Данные хранятся только на устройстве, внешний сервер не рассматривается. Наличие дальномера не обязательно: значения можно вводить вручную, поэтому измерения — самостоятельная сущность, а не побочный продукт BLE-сессии.

Доменная модель ещё меняется. Уже сейчас нужен комментарий к измерению, позже появятся метки, проекты, планы и фотографии. Готовой схемы хранения в проекте нет: `SharedPreferences` используется только для настроек и последнего устройства.

Ограничения окружения: `minSdk = 24`, `allowBackup = false`, приложение небольшое, а критична скорость разработки и прозрачность данных.

## Решение

Каждый список измерений — отдельный JSON-документ в `filesDir/measurements/<uuid>.json`. Имя списка хранится внутри документа, а не в имени файла.

- Формат описан `kotlinx.serialization`; документ содержит `schemaVersion`, `id`, `name`, `createdAt`, `updatedAt` и массив измерений.
- Измерение хранит десятичную строку значения и единицу (`LengthUnit`), а не `Double`. Это сохраняет точность и то значение, которое видел пользователь; пересчёт в другие единицы при необходимости делается через `BigDecimal`.
- Любое изменение (создание, добавление, правка, удаление, переименование) сразу пишется на диск. Отдельной кнопки «Сохранить» нет.
- Запись атомарная: временный файл → `fsync` → `rename`, предыдущая версия остаётся в `.bak`. При чтении сначала пробуется основной файл, затем резервный.
- Доступ к документам идёт через `MeasurementListRepository`. UI и ViewModel не знают, что под интерфейсом JSON.
- При старте читаются все документы каталога и в памяти остаются только сводки для экрана списка. Полный документ загружается при открытии.

## Последствия

- Данные полностью локальны и читаемы; их легко экспортировать и отлаживать.
- Пока документов и измерений немного, чтение каталога при старте незаметно. При росте объёма появится отдельный индекс или переезд на Room — за тем же интерфейсом репозитория.
- Каждое изменение перезаписывает документ целиком. Для списков в сотни измерений это приемлемо; для десятков тысяч потребуется другой backend.
- Нет запросов между документами (например, «все измерения проекта»). Такие выборки появятся вместе с проектами и станут поводом перейти на Room.
- `allowBackup = false` означает, что при переустановке данные теряются. Это осознанно отложено до появления экспорта или смены способа хранения.
- Формат версионирован полем `schemaVersion`; миграции выполняются при чтении, старые файлы не переписываются без изменений.
- Появляются юнит-тесты на сериализацию, валидацию ввода и репозиторий, не требующие Android-устройства.

## Альтернативы

- **Room/SQLite сразу.** Даёт запросы, инкрементальную запись и связи проект → измерения → фото, но требует KSP, миграций и фиксированной схемы, пока модель ещё формируется. Переезд на Room остаётся возможен за интерфейсом репозитория.
- **`SharedPreferences`.** Не предназначена для списков и больших значений, плохо версионируется и неудобна для экспорта.
- **Один общий файл на все измерения.** Не позволяет независимо открывать, переименовывать и удалять списки, а повреждение файла теряет всё сразу.
- **NDJSON с дописыванием.** Быстрая запись серии, но редактирование и удаление требуют компакции, а документ перестаёт быть простым и читаемым.
