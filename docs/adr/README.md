# Архитектурные решения (ADR)

Каталог фиксирует значимые архитектурные решения и причины, по которым они приняты. ADR отвечает на вопрос «почему так», а не «как устроено»: текущее устройство описано в `AGENTS.md` и коде.

## Когда нужен ADR

- выбор архитектурного подхода или границ модулей;
- владение состоянием и жизненным циклом (BLE-сессия, настройки, навигация);
- публичные контракты между модулями (например, кодек протокола);
- добавление или замена зависимости, заметная для архитектуры;
- решение, которое дорого откатить или которое затрагивает несколько экранов и модулей;
- осознанный отказ от очевидного варианта, если причина не видна из кода.

ADR не нужен для багфиксов, переименований, локального рефакторинга и правок интерфейса, не меняющих архитектуру.

## Правила

- Один ADR — одно решение.
- Имя файла: `NNNN-short-title-in-english.md`, где `NNNN` — сквозной номер с ведущими нулями. Номера не переиспользуются.
- Статусы: `Proposed`, `Accepted`, `Superseded by NNNN`, `Deprecated`.
- Принятый ADR не переписывается. Изменение оформляется новым ADR; старый получает статус `Superseded by NNNN`.
- Индекс ниже обновляется при добавлении ADR и смене статуса.
- Язык документа — русский, имена файлов — английский, как и в остальном проекте.
- Обязательные разделы: «Контекст», «Решение», «Последствия», «Альтернативы». Шаблон — `template.md`.
